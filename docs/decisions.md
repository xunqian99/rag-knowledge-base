## 001 · 用 Docker Compose 编排三个中间件

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

用一份 `docker-compose.yml` 声明式拉起三个服务,数据用命名卷持久化:

| 服务 | 镜像 | 端口 |
|---|---|---|
| PostgreSQL + pgvector | `pgvector/pgvector:pg16` | 5432 |
| Elasticsearch | `elasticsearch:8.15.0` | 9200 |
| Redis | `redis:7-alpine` | 6379 |

### 为什么需要它

项目要存三类数据,单个关系型数据库不够:

- **文档分块 + 向量** → PostgreSQL + pgvector
- **关键词全文检索** → Elasticsearch(第 13 项做混合检索时用)
- **重复提问的缓存** → Redis(第 22 项用)

这些属于基础设施,不是业务代码。先用容器起好,后面所有功能都建立在它上面。

### 关键决策

**1. 镜像用 `pgvector/pgvector:pg16`,不用官方 `postgres:16`**

官方镜像里没有 `vector` 这个数据类型,需要自己编译 C 扩展。pgvector 官方镜像已经把扩展预装好了。

**2. Elasticsearch 关闭安全认证(`xpack.security.enabled=false`)**

ES 8 默认开启 HTTPS + 账号密码,Java 客户端不配证书会直接连接失败。开发环境图省事关掉。

**这是一个明确的取舍,不是疏忽。** 生产环境必须开回来,走 HTTPS + 账号认证。

**3. 数据持久化用命名卷,不用绑定挂载**

命名卷由 Docker 托管,避免 Windows 下的文件权限问题,也不会把数据库文件混进项目目录。

反过来,初始化 SQL 脚本用的是绑定挂载(`./init:/docker-entrypoint-initdb.d:ro`),因为需要随时编辑查看。**这个对比本身就是面试常考题。**

**4. 限制 ES 堆内存为 512m**

ES 默认按物理内存比例分配堆,能占用 2GB 以上,在笔记本上严重拖慢速度。

### 备选方案与放弃原因

| 方案 | 放弃原因 |
|---|---|
| 三个 `docker run` 命令手动启动 | 参数散落在命令行,无法复现,换台机器就得重新拼 |
| 在 Windows 本地直装三个服务 | pgvector 需自行编译 C 扩展;Redis 无官方 Windows 版本 |
| 用云数据库(阿里云等) | 有成本、需配网络白名单,学生项目不划算 |

### 其他

- 三个服务在同一个默认 bridge 网络里,互相可用**服务名**当主机名访问(如 `postgres:5432`)
- 宿主机上的应用则通过 `localhost:5432` 访问,靠端口映射打通
- `.env` 存密码,已加入 `.gitignore`;仓库里只提交 `.env.example`

### 验证结果

- `docker compose config` 通过
- 三个容器均正常运行,5432 / 9200 / 6379 三个端口处于监听状态
- `pg_extension` 中可见 `vector`
- ES 9200 返回版本 `8.15.0`
- Redis `ping` 返回 `PONG`

### 面试可能被追问

1. Docker Compose 和 `docker run` 的本质区别?(声明式 vs 命令式,可版本化、可复现)
2. ES 关掉安全认证的风险是什么?生产环境你会怎么处理?
3. 命名卷和绑定挂载的区别?为什么数据库用前者、配置用后者?
4. 容器之间怎么互相访问?(默认 bridge 网络 + 服务名 DNS 解析)

## 002 · 搭建 Spring Boot 工程骨架,接通 PostgreSQL 与 Redis

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

在 `rag-server/` 下建立 Maven 工程,依赖为 web / data-jpa / data-redis /
actuator / postgresql 驱动 / lombok / test,并在 `application.yml` 中
配置好 PostgreSQL 与 Redis 的连接。

### 为什么需要它

这是整个后端服务的「壳体」,后面 20 多项功能都往里面加代码。
数据库连接是第 3 项建表的前提。

### 关键决策

**1. Spring Boot 版本从 4.1.1 降到 3.5.x**

Initializr 默认生成的是 4.1.1,依赖坐标是 `spring-boot-starter-webmvc`。
经查证:

- `spring-boot-starter-webmvc` 这个坐标**从 4.x 才开始存在**,Boot 3 时代叫 `spring-boot-starter-web`
- LangChain4j 的主力 starter 最新为 `1.20.0-beta30`,其依赖声明中绑定的是 **Spring Boot 3.5.13**
- LangChain4j 虽然也发布了 Boot 4 版本(如 `langchain4j-open-ai-spring-boot4-starter`),但那是新分支,资料少

结论:本项目主要靠 AI 辅助开发,而 AI 与社区资料对 Boot 3 的支持度远高于 Boot 4;
接 LangChain4j 时 Boot 3 的路径更稳。**选 3.5.x,不选 4.x。**

**2. 具体版本选 3.5.7 而非 3.5 线最新的 3.5.16**

本机 Maven 仓库已缓存 3.5.7 的全套依赖,首次编译几乎零等待;
升级到 3.5.16 需重新下载 100MB 以上依赖。
补丁版本不影响功能,这是典型的**「稳定可用优先于版本最新」**取舍。

**3. 用 yml 而不是 properties 格式**

yml 用缩进表达层级,支持列表和嵌套结构,可读性更好。
注意 yml 里必须写成 `spring:` 换行缩进 `application:` 的形式,
写成 `spring.application.name=xxx` 是 properties 语法,Spring Boot 读不到。

**4. `ddl-auto: none` —— 不用 JPA 自动建表**

JPA 自带的 `ddl-auto: update` 能自动建表,但**本项目不能用**:
分块表里含 `vector` 类型字段,Hibernate 不认识这个类型,
自动建表会漏字段甚至直接报错。因此表结构改由手写 SQL 管理(见第 3 项)。

**5. `open-in-view: false` —— 关闭 OSIV**

OSIV(Open Session In View)默认开启时,数据库连接会一直被持有到
HTTP 响应结束,高并发下连接池会被瞬间打满。
关掉它,让事务边界清晰收缩到 Service 层。

**6. 数据库密码走环境变量占位符**

写成 `password: ${DB_PASSWORD:rag123456}`,优先读环境变量,读不到才用默认值。
密码不硬编码在代码里,生产环境直接注入环境变量即可。

### 备选方案与放弃原因

| 方案 | 放弃原因 |
|---|---|
| 用 IDEA 的 New Project 向导生成 | 目录结构与配置内容由向导决定,不易统一控制 |
| 用 Maven archetype 命令行生成 | 生成的是老式骨架,需大量手工修改 |
| 用 Spring Initializr 网站下载 zip | 本质同向导,还要手工解压 |

### 验证结果

```
mvn -q clean compile          → EXIT=0
mvn test                      → BUILD SUCCESS
  HikariPool-1 - Start completed.        ← 证明已成功连上 PostgreSQL
  Tests run: 1, Failures: 0, Errors: 0
```

## 003 · 用 Flyway 管理表结构,建四张业务表

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

引入 Flyway 作为表结构版本管理工具,并建立四张表:

| 表 | 作用 |
|---|---|
| `document` | 文档元信息:文件名、类型、大小、存储路径、处理状态、块数量 |
| `document_chunk` | 分块文本 + `vector(1024)` 向量 + JSONB 元数据(**项目核心**) |
| `chat_session` | 一次会话 |
| `chat_message` | 每条问答,含引用来源数组、耗时 |

### 为什么需要它

表结构定义了整个项目的数据形态,后续所有功能都围绕它读写。
而分块表带 `vector` 类型字段,JPA 的 `ddl-auto` 不认识这个类型,
所以自动建表这条路走不通,必须改由 SQL 脚本管理。

### 关键决策

**1. 用 Flyway,而不是手动连数据库执行 SQL**

Flyway 相当于「数据库表结构的 Git」:每次改动是一个 `V<n>__描述.sql` 文件,
应用启动时自动执行未执行过的脚本,并把执行记录写进 `flyway_schema_history` 表。

解决的问题:多人协作时每个人本地库结构不一致、改动无法追溯、
部署到测试/生产环境要重复手工操作。

**2. Flyway 10 以后必须额外加 `flyway-database-postgresql`**

Flyway 从这个版本起把各数据库的支持拆成了独立模块。
只加 `flyway-core` 会在启动时报「Unsupported Database: PostgreSQL」。
本项目实际用到的是 Flyway 11.7.2。

**3. 向量索引用 HNSW,不用 IVFFlat**

- IVFFlat 需要先用真实数据「训练」聚类中心,数据量少时召回效果差
- HNSW 建索引慢、占内存多,但查询又快又准,且不依赖训练数据

学生项目数据量不大,HNSW 更稳。索引参数用默认值(m=16, ef_construction=64)。

**4. 向量距离用余弦(`vector_cosine_ops`)**

余弦距离只比较向量方向、不受长度影响,是文本 embedding 的常规选择。
pgvector 另外还支持 L2 欧氏距离和内积。

**5. 主键用 `BIGSERIAL` 而不是 UUID**

自增整数索引更紧凑、插入局部性好、调试时肉眼可读。
UUID 的优势在分布式生成和不被猜测,本项目用不上。

**6. 删除用 `ON DELETE CASCADE`**

删 `document` 一行,它的所有分块自动跟着删。
不用在代码里写两遍删除逻辑,也不会留下孤儿数据。
生产环境更常用软删除(加 `deleted` 标记位),这个取舍面试常被问。

**7. 会话拆成 `chat_session` + `chat_message` 两张表**

引用来源、耗时这类信息属于「某一条回答」而非「整个会话」。
现在拆开,第 8 项多轮对话、第 21 项首字延迟统计都不需要再改表。

**8. 状态字段不加 CHECK 约束**

`status`、`role` 这类枚举交给应用层控制。
好处是以后新增状态不需要动表结构,代价是数据库层面少了一层兜底校验。

**9. `embedding` 列允许为 NULL**

入库时先写文本块,向量是调用 embedding 接口后才回填的。
允许 NULL 才能支持「先入库、后异步生成向量」这个流程(第 7 项)。

**10. 加 `UNIQUE (document_id, chunk_index)` 约束**

第 12 项重新索引时会「先删旧块、再插新块」,
这个约束能在代码出 bug 时拦住重复数据。

### 备选方案与放弃原因

| 方案 | 放弃原因 |
|---|---|
| JPA `ddl-auto: update` 自动建表 | 不支持 `vector` 类型,直接出局 |
| 手写 SQL,手工连库执行 | 改动无法追溯,多人协作时各人库结构不一致 |
| Liquibase | 功能类似,但配置用 XML/YAML,比纯 SQL 啰嗦 |

### 关于向量维度

按百度千帆 `bge-large-zh` 的 **1024 维** 建表。
该数字尚未用真实 API 响应核对,第 7 项首次调用 embedding 接口时会验证实际长度;
若不符,通过新增 `V2__` 迁移脚本调整维度 —— 这正好是 Flyway 价值的实际演示。

### 验证结果

```
mvnw test  →  BUILD SUCCESS
  Migrating schema "public" to version "1 - init schema"
  Successfully applied 1 migration to schema "public", now at version v1
```

直接连接数据库核对结果:

- 五张表存在:`document` / `document_chunk` / `chat_session` / `chat_message`
  / `flyway_schema_history`
- `document_chunk.embedding` 的列类型为 `vector`
- pgvector 扩展版本 **0.8.6**
- 八个索引齐全,含 `idx_chunk_embedding_hnsw` 与 `uk_chunk_document_index`
- `flyway_schema_history` 中 V1 记录 `success=true`,耗时 156ms

## 004 · 健康检查接口(两层设计)

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

新增 `cn.ragserver.health` 包,包含:

| 类 | 职责 |
|---|---|
| `DependencyChecker` | 探测器接口,新依赖只需新增实现类 |
| `DatabaseChecker` | 探测 PostgreSQL |
| `RedisChecker` | 探测 Redis |
| `SystemHealthService` | 并行探测 + 超时控制 |
| `HealthReport` | 返回体(record) |
| `HealthController` | 暴露 `GET /api/system/health` |

### 关键决策

**1. 健康检查分两层,职责不同**

- `/actuator/health` —— 给运维和容器编排用,格式由 Spring 决定,
  会输出数据库地址、驱动版本等内部信息,**不适合直接对公网开放**
- `/api/system/health` —— 给前端用,字段自己定义,只暴露必要信息

**2. 最终没有写自定义 HealthIndicator**

原计划要写一个,但评估后发现:Actuator 自带的 `db` 和 `redis` 指示器
已经覆盖了当前全部依赖,再写一个只是重复劳动。

等第 7 项接入大模型 API 时才有必要 —— 那个依赖 Actuator 不认识,
届时写自定义 `HealthIndicator` 才有实际价值。**不为用某个机制而用。**

**3. 并行探测 + 单个依赖独立超时**

探测在专用线程池里并行执行,总耗时约等于最慢的那一个,而不是各项相加。
每个探测加 `orTimeout(2000ms)`,超时直接判 DOWN。

反过来,如果一个卡住的 Redis 把整个健康检查接口吊死,
监控系统反而什么都看不到。

**4. 专用线程池,线程数为探测器数量,设成守护线程**

不复用 Tomcat 的业务线程:依赖一慢,大量业务线程会被占住,服务雪崩。
线程池在 `@PreDestroy` 里关闭,否则反复重启上下文会泄漏线程。

**5. 用注入的 `DataSource`,不用 `DriverManager.getConnection()`**

健康检查要探测的是「应用真正用的那条链路」。
自己新建连接会绕开连接池 —— 可能出现连接池已打满、业务已经借不到连接,
而自检却显示正常的情况,这就失去意义了。

**6. 全部健康返回 200,否则返回 503**

不是「永远返回 200,状态写在 body 里」。因为监控系统、负载均衡、
K8s 探针都是看 HTTP 状态码决定要不要告警、要不要摘流量的。
状态码不对,它们就看不见问题。返回体照常给出,方便排错。

**7. `HealthReport.isUp()` 加 `@JsonIgnore`**

Jackson 会把 `isXxx()` 形式的方法当成属性 getter,自动序列化出
一个多余的 `"up"` 字段。而 `status` 已经表达同样信息,接口契约应当保持精简。

### 已知局限(诚实记录)

- `orTimeout` 只会让 `CompletableFuture` 提前完成,**不会中断底层调用**。
  也就是说探测超时后,那个线程仍可能阻塞在 JDBC 上,直到驱动自己超时。
  更彻底的做法是给底层连接设置 socket 超时,或使用可中断的异步客户端。
- Hikari 的 `connection-timeout` 是 30s,比健康检查的 2s 长。
  生产环境应把两者对齐,否则超时的探测会留下"挂着"的线程。

### 观察到的现象

| 调用次序 | PostgreSQL | Redis | 总耗时 |
|---|---|---|---|
| 第 1 次 | 3 ms | **550 ms** | 553 ms |
| 第 2 次 | 2 ms | **1 ms** | 2 ms |

原因:Lettuce 的 TCP 连接是**懒加载**的,第一次调用时才真正建连。
这提示了一个优化方向 —— 可以在应用启动后预热连接(第 23 项考虑)。

### 验证结果

```
GET http://localhost:18080/api/system/health  →  HTTP 200

{"status":"UP",
 "checkedAt":"2026-09-19T11:48:14.403Z",
 "costMs":553,
 "dependencies":[
   {"name":"PostgreSQL","status":"UP","costMs":3,"error":null},
   {"name":"Redis","status":"UP","costMs":550,"error":null}]}
```

注:`checkedAt` 是 UTC 时间(带 `Z` 后缀),比本地时间早 8 小时。
这是 `Instant` 的正确行为 —— 时间戳统一用 UTC 存储和传输,
由展示层转换成用户所在时区。

## 005 · 文件上传接口 + 全局异常处理

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

新增 `cn.ragserver.common` 与 `cn.ragserver.document` 两个包:

| 类 | 职责 |
|---|---|
| `Document` / `DocumentRepository` | JPA 实体与数据访问 |
| `DocumentStorage` | 把文件写到本地磁盘,含路径越界防护 |
| `DocumentService` | 校验 → 落盘 → 入库 → 失败补偿 |
| `DocumentController` | `POST /api/documents` |
| `BusinessException` / `ApiError` / `GlobalExceptionHandler` | 统一异常处理 |

### 关键决策

**1. 文件存磁盘,不存数据库 BLOB**

存数据库会让备份体积暴涨、查询变慢、连接被大文件占住。
生产环境应换对象存储(MinIO / 阿里云 OSS),这条写进 README 的「上生产要改什么」。

**2. 磁盘文件名用 UUID,不用用户传上来的名字**

直接用原始文件名会踩两个坑:

- **路径穿越**:文件名传成 `..\..\Windows\System32\xxx`,拼接后直接写到系统目录
- **重名覆盖**:两个人都传 `report.pdf`,后者覆盖前者

所以磁盘名用随机 UUID,原始名单独存进 `document.file_name` 字段。

另外 `DocumentStorage.resolveSafely()` 里还有一层「解析后的路径必须以存储根目录开头」
的校验 —— 这是**纵深防御**,即使上游逻辑被改错,这一层仍然拦得住。

**3. 上传大小限制必须显式修改**

Spring Boot 默认单文件 **1MB**、单请求 10MB。
不改的话传一个几 MB 的 PDF 直接抛 `MaxUploadSizeExceededException`。
本项目配置为单文件 50MB、单请求 50MB。

注意这个异常发生在进入 Controller 之前,业务代码里 catch 不到,
只能在 `@RestControllerAdvice` 里处理。

**4. 先写盘、后入库,失败时保守清理**

两种顺序的失败模式完全不同:

| 顺序 | 崩在中间的结果 | 危害 |
|---|---|---|
| 先写盘、后入库 | 多一个没人引用的孤儿文件 | 浪费磁盘,**安全** |
| 先入库、后写盘 | 库里有记录但文件不存在 | 用户看得到、打不开,**事故** |

所以选前者。而清理孤儿文件时必须保守 —— **宁可漏删,不可误删**:

```
入库抛异常
  ├─ 查到记录已存在(异常发生在提交之后)→ 保留文件
  ├─ 确认没有这条记录             → 删除文件
  └─ 查询本身也失败               → 保留文件,只记日志
```

最后一条最关键:确认不了的时候选择不删。因为「不删」最坏是多一个孤儿文件,
「删」最坏是删掉一个已被引用的文件,两者代价不对等。

**5. 用 `saveAndFlush` 而不是 `save`**

`save` 可能把真正的 INSERT 推迟到方法结束提交时才发生,失败点不明确。
`saveAndFlush` 立即执行并提交,让「数据库到底成没成功」在代码里有个清晰判断点。

**6. 扩展名用白名单校验**

黑名单永远列不全,白名单只要没写进去就一定拦得住。
白名单放在配置里,第 9 项支持 PDF/Word/Excel 时只需要加几个后缀。

**7. 统一异常处理,且兜底异常绝不返回原始信息**

未预期异常的 `getMessage()` 里常含表名、SQL 片段、文件路径甚至连接串,
直接返回等于给攻击者递情报。所以兜底处理器只返回一句通用提示,
详细信息写服务端日志。

**8. 单独处理 `NoResourceFoundException`**

这个坑很隐蔽:兜底的 `Exception` 处理器会把所有异常变成 500,
于是 URL 打错一个字母也会返回「服务内部错误」,让人误以为服务真的坏了。
Spring 6.1 起找不到静态资源会抛这个异常,必须单独接住并返回 404。

**9. 返回 201 而不是 200**

语义上「创建了一个新资源」。同时提示调用方这不是幂等操作 ——
重复上传会创建多条记录,不要盲目重试。

**10. 返回 DTO,不直接返回实体**

实体字段随表结构变化,而接口契约应当稳定;
序列化实体还可能触发 Hibernate 懒加载的意外查询。

**11. `@Enumerated(EnumType.STRING)` 而不是默认的 ORDINAL**

ORDINAL 存的是枚举序号 0/1/2/3,以后在枚举中间插一个新值,
已有数据的含义就整体错位了。这是 JPA 里非常经典的一个坑。

```
   {"id":1,"fileName":"员工手册-节选.txt","fileType":"txt","fileSize":2570,
```

## 006 · 文本切分成段落(朴素版)

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

上传流程接上后半段,并新增:

| 新增 | 作用 |
|---|---|
| `DocumentChunk` / `DocumentChunkRepository` | 分块实体与数据访问 |
| `TextSplitter` | 编码探测 + 按空行切分 |
| `DocumentIndexService` | 事务化的索引流程 |
| Flyway `V2` 迁移 | 给 `document` 加 `error_message` 字段和状态索引 |

### 关键决策

**1. 先做「朴素版」切分,故意留出问题**

本项只按空行切段落,不做长度控制。第 10 项才升级为「按标题层级切分 + 长度/重叠可配置」。

这样做是为了留下**基线**:第 20 项要用数据证明改进有效,没有基线就没法对比。
同时,亲手跑出问题比听人讲更有印象。

**2. 中文文本的编码探测:严格 UTF-8 → 回退 GB18030**

Windows 上不少中文 txt 是 GBK/GB18030,直接按 UTF-8 读会得到乱码。

处理顺序:去 BOM → 严格模式 UTF-8 → 回退 GB18030 → 都失败则明确报错。

**关键在「严格」**:宽松模式会把非法字节静默替换成 U+FFFD,
程序不报错但内容已经坏了,反而更难发现。严格模式会抛异常,才有机会走回退分支。

最后选择「明确失败」而不是「塞一堆问号糊弄过去」—— 一份内容坏掉的语料
会在检索阶段造成更隐蔽的问题。

**3. JPA 实体不映射 `embedding` 和 `metadata` 两列**

Hibernate 不认识 `vector` 类型,硬映射会启动报错。
而且本项根本不写向量,让它保持 NULL 即可。第 7 项写入向量时改用原生 SQL。

通用说法:JPA 实体只需要映射「业务代码要用到的列」,不是数据库表的逐字段镜像。

**4. 分块表用普通的 `documentId` 字段,不用 `@ManyToOne` 关联**

| 方案 | 优点 | 缺点 |
|---|---|---|
| `@ManyToOne` | 符合 JPA 习惯,`chunk.getDocument()` 直接可用 | 批量插入时要维护实体引用;容易触发懒加载意外查询 |
| 普通 `Long documentId` | 简单、可预测、无懒加载陷阱 | 需要自己保证外键正确 |

分块表是「子表」且数量大,选前者更省心。这是取舍,不是对错。

**5. `@Transactional` 必须放在独立的 Bean 里**

**这是 Spring 里非常经典的坑**:`@Transactional` 靠 AOP 代理实现,
外部调用会经过代理;但**类内部的方法互相调用不经过代理**,
事务注解会静默失效 —— 不报错、不警告,只是没生效。

所以索引逻辑单独放进 `DocumentIndexService`,由 `DocumentService` 从外部调用,
事务才真正生效。

**6. 上传和索引分成两个事务**

合成一个事务的话,切分失败会把文档记录一起回滚,用户只能重新上传。

分开之后:第一个事务保证「文件 + 文档记录」落地,第二个事务负责「切分 + 分块 + 状态」。
切分失败仍然留下一条 `status=FAILED` 的记录 —— 第 12 项可以点「重新索引」,
第 23 项能自动重试。

**7. 失败原因单独用一个事务写入**

`markFailed` 上是 `@Transactional`。因为调用它时 `index()` 的事务已经回滚,
失败标记必须写在事务之外才能落库。

**8. 更新文档状态时不显式调用 `save`**

`document` 是从 repository 查出来的托管对象,修改字段后 Hibernate 会在
事务提交时自动比对并发出 UPDATE,这叫**脏检查**。显式 `save` 不会错,只是多余。

**9. 逐行扫描切分,不用正则**

正则在处理「连续多个空行」「行尾空格」「混用换行符」时很容易写错且不好调。
逐行扫描虽然多几行代码,但意图清晰、行为可预测。

### 已知问题(留给第 23 项)

**`IDENTITY` 主键会让 Hibernate 无法批量插入。**

`document_chunk` 用 `BIGSERIAL` + `GenerationType.IDENTITY`,
而 IDENTITY 需要每插一行就拿一次自增 ID,所以 Hibernate 会**自动关闭 JDBC 批处理**。
`saveAll(50 条)` 实际发出的是 50 条独立的 INSERT。

解决方向:改用 `SEQUENCE` 主键 + `allocationSize`,或用
`JdbcTemplate.batchUpdate` 绕过 Hibernate。留到第 23 项做性能优化时处理,
届时先测出真实耗时,再改,再对比。

### 观察到的数据

样例文档《员工手册-节选》(2570 字节)切分结果:

| 指标 | 值 |
|---|---|
| 分块数 | 19 |
| 最短 / 最长 / 平均 | 8 字 / 106 字 / 55 字 |
| 过短的块(< 25 字) | 5 个,全部是纯标题 |

**这 5 个纯标题的块就是朴素切分的缺陷**:检索命中它们时,
大模型拿到的只是一句「第二章 费用报销」,什么都答不出来。
第 10 项会针对性地解决,第 20 项用指标证明解决有效。

## 007 · 接入向量模型,把分块向量写进 pgvector

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

接入百度千帆 v2 的 `bge-large-zh` 向量模型,给每个分块生成向量并写入 `pgvector`。

新增 `cn.ragserver.embedding` 包与 `DocumentChunkVectorDao`。

### 关键决策

**1. 走千帆 v2 的 OpenAI 兼容接口,复用 LangChain4j 的 OpenAI 客户端**

千帆有两代认证:

| 代次 | 地址 | 认证 |
|---|---|---|
| 第一代 | `aip.baidubce.com` | API Key + Secret Key 换 access_token |
| **第二代** | `qianfan.baidubce.com/v2` | 单个 API Key 作 Bearer Token |

选第二代:少一次换 token 的网络往返,也不用自己处理 token 过期。
因为它兼容 OpenAI 协议,直接复用 `langchain4j-open-ai`,只是换了个 baseUrl。

**2. 用 `EmbeddingModel` 抽象,而不是自己拼 HTTP 请求**

LangChain4j 提供了统一的 `EmbeddingModel` 接口。
以后要从百度换成通义或 OpenAI,业务代码一行都不用改,只改配置。
它同时封装了重试和异常处理。

**3. 缺少密钥时服务照常启动,只让对应功能不可用**

没有在 `EmbeddingConfig` 里直接抛异常拒绝启动,而是用一个占位值把 Bean 建出来,
真正的校验推迟到 `EmbeddingService` 调用前。

理由:一个服务应该做到「某个外部依赖没配好时服务本身照常运行」,
而不是整个应用起不来。否则运维半夜收到「服务挂了」的告警,实际只是少配了一个密钥。

**4. 健康检查只检查「密钥配没配」,不真的调接口**

这是个刻意的取舍。健康检查会被监控系统每隔几秒调用一次,如果每次都真的调向量接口:

1. 持续消耗 API 额度(按调用量计费)
2. 外部接口慢,会把健康检查响应时间拖长,监控反而失真
3. 网络抖动时频繁误报,产生无意义告警

配置类问题在健康检查里暴露,连通性问题留给实际业务调用去发现。
**如果确实需要探测连通性,应该单独做低频定时探测,而不是塞进健康检查接口。**

**5. 主动校验向量维度,并给出可操作的报错**

数据库列是 `vector(1024)`。如果模型实际输出别的维度,写入时数据库会直接报错,
但错误信息很可能让人摸不着头脑。

所以在第一次拿到结果时主动比对,报错信息里直接写清楚
「该改哪个配置、该加什么迁移脚本」。

**6. 向量写入用 JDBC 原生 SQL,不走 JPA**

Hibernate 不认识 `vector` 类型,硬支持要写自定义 UserType,代码量大收益小。
需求只是一条 UPDATE,用 `JdbcTemplate` 最省事。

用 `CAST(? AS vector)` 而不是 `?::vector` —— 后者和 JDBC 的占位符写在一起
容易产生解析歧义。

**7. 这里的 `batchUpdate` 能真正生效**

和分块的 INSERT 不同:UPDATE 不涉及自增主键生成,
所以 JDBC 批处理不会被 Hibernate 关掉。多条 UPDATE 会合并成批发送。

### 踩到的坑:密钥文件放在 `src/main/resources` 是错的

**现象**:密钥明明填对了,程序读到的却还是占位符。

**原因**:`application-local.yml` 放在 `src/main/resources/` 下,会被**打包进 jar**。
重新运行旧 jar 时,读到的自然是构建时那份旧文件。

**两个后果**:

1. 每次改密钥都必须重新构建,很别扭
2. **更严重的是,密钥被打进了构建产物**
   —— 如果把这个 jar 发给别人或传到服务器,密钥就跟着走了

**正确做法**:把 `application-local.yml` 放在**项目根目录**(即应用的运行目录),
不要放进 `src/`。

Spring Boot 的配置文件搜索路径是:

```
classpath:/application.yml            (打进 jar 的默认配置)
classpath:/config/application.yml
file:./application.yml                 (运行目录,优先级更高)
file:./config/application.yml          (优先级最高)
```

放在运行目录的文件优先级高于 jar 内的,而且**不会被纳入构建产物**。

**这条经验可以推广成一句话:密钥类的配置要放在构建产物之外。**

### 验证结果

```
POST /api/documents  →  HTTP 201
{"id":5,"status":"INDEXED","chunkCount":19,"errorMessage":null}

数据库核对:
  分块总数=19  有条向量的=19
  维度范围=[1024, 1024]
  向量模长范围=[1.0000, 1.0000]
```

**第 6 项里那个悬而未决的「1024 维」至此得到确认** —— 模型实际输出就是 1024 维,
和建表时的假设一致,不需要迁移。

用 SQL 直接做的一次相似度检索,结果语义合理:

```
以第 3 块「1.1 工作时间」为基准,最相似的三个分块:
  0.8888  [2] 1.1 工作时间 / 公司实行标准工时制...
  0.8737  [5] 1.4 请假流程 / 请假需至少提前 1 个工作日...
  0.8717  [4] 1.3 迟到与早退 / 每月累计迟到超过 3 次...
```

最相似的确实是同一章节(考勤管理)的内容。

### 额外发现:向量是归一化的

所有向量的模长都精确等于 **1.0000**,说明 `bge-large-zh` 输出的是单位向量。

这意味着:**余弦相似度和内积在数学上完全等价**。

因此索引里的 `vector_cosine_ops` 可以换成 `vector_ip_ops`(内积)。
内积的计算少一步开方和除法,理论上更快。当前数据量下差异可以忽略,
所以没有改;但这是个值得知道的优化点,面试被问到「余弦和内积怎么选」时可以直接讲。

## 008 · 问答接口(第一个完整可用的 RAG)

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

新增 `cn.ragserver.chat` 与 `cn.ragserver.retrieval` 两个包,打通完整链路:

```
问题 → 向量化 → pgvector 检索 TOP K → 组装 prompt → 调大模型 → 返回答案 + 引用
```

### 关键决策

**1. 对话模型复用同一个千帆 Key 和同一个 OpenAI 兼容客户端**

配置里 `rag.chat.api-key` 默认取 `rag.embedding.api-key`,
而不是再写一遍。**同一份密钥出现在两个地方,改一处漏一处是安全事故的常见来源。**

**2. Prompt 的防幻觉指令是全项目投入产出比最高的一段文字**

系统指令里最关键的是这一条:

> 如果【参考资料】中没有能够回答问题的内容,直接回复:资料中没有找到相关内容。

实测有效:问「年假有多少天?」时,文档里虽然出现过"年假"这个词
(「年假需提前 3 个工作日申请」),但并没有写天数。
模型没有编造,而是老实回答「资料中没有找到相关内容」。

**不加这一句,模型会非常自然地用自己的知识补全答案** ——
用户看到一段流畅自信、却和知识库毫无关系的回答,这比直接说「没找到」危险得多。

**3. 温度设为 0.2**

事实型问答要的是稳定。同一个问题问两次得到不同答案,用户体验很差,
也没法做评测对比。

**4. 检索结果为空时不调用大模型**

prompt 里一条资料都没有,模型也只能说不知道,
这一次调用纯属浪费钱和时间。直接返回固定话术。

**5. 引用溯源:从答案正文解析 `[n]` 标记,只返回真正用到的来源**

第一版是「把检索到的 TOP K 全部当成引用返回」,结果发现一个明显的问题:

> 问「年假有多少天?」,答案是「资料中没有找到相关内容」,
> 引用列表里却仍然列着三条 —— 用户点进去会发现完全对不上。

修正做法:用正则从答案里解析出 `[1][2]` 这类标记,
只返回被真正引用到的那些。因为检索固定返回 TOP K 条,
但模型实际只用其中一两条,**把没用到的一起返回等于在乱指**。

模型没标注来源时返回空列表,并记一条 debug 日志,方便回头调 prompt。

**6. 事务边界:只把写库放进事务,不把外部调用包进去**

对话接口要调两次外部 API(向量 + 对话),可能耗时好几秒。
如果把整个流程包在一个事务里,数据库连接会被长时间占用,
并发一高连接池就爆了。所以持久化单独放在 `ChatHistoryService` 里。

### 实测发现:朴素切分的危害有了数据

问「出差住宿能报多少?」时,检索结果排序是:

| 排名 | 相似度 | 内容 |
|---|---|---|
| 1 | 0.7928 | **第二章 费用报销** ← 光秃秃的标题,没有正文 |
| 2 | 0.7852 | 2.1 报销标准 / 出差住宿:一线城市每晚不超过 500 元… ← **真正的答案** |
| 3 | 0.7477 | 第一章 考勤管理 |

**没有任何正文的标题块,排名居然比含答案的块还高。**
这次没答错,只是因为 K=3 把正确答案也捞了进来 ——
**如果 K=1,这题就答错了。**

这是第 6 项「故意先做朴素版」的直接证据,第 10 项会针对性解决,
第 20 项用指标量化改进幅度。

## 009 · 接入 Apache Tika,支持 PDF / Word / Excel

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

| 新增/改动 | 说明 |
|---|---|
| 引入 Tika 3.2.3 | `tika-parsers-standard-package`,底层调度 PDFBox 与 POI |
| `DocumentTextReader` | 所有格式的统一入口,按格式分流 |
| `TextSplitter` | 移除解码逻辑,只负责切分(职责收窄) |
| 白名单放开 | `txt` → `txt / pdf / docx / xlsx` |
| 文本长度上限 | `rag.storage.max-text-length`,默认 500 万字符 |

### 关键决策

**1. 用 Tika,不自己写解析器**

pdf / docx / xlsx 的内部结构都不是文本:docx 和 xlsx 其实是 zip 包(内含 XML),
pdf 是二进制对象流,文字可能被拆成绘制指令,还可能是扫描图片。
自己写不现实。Tika 负责格式识别 + 调度底层解析器 + 统一输出纯文本。

**代价**:连带引入 PDFBox、POI 等几十个依赖;解析本身也是攻击面。这个代价必须付。

**2. 按格式分流:txt 走自研解码,其余走 Tika**

**Tika 对纯文本的默认假设是 UTF-8(除非文件带 BOM)**,而 Windows 上
GBK/GB18030 编码的中文 txt 相当常见 —— 交给 Tika 会乱码。

我们在第 6 项验证过「严格 UTF-8 → 回退 GB18030」这套探测是有效的,继续用。

这不是偷懒,是两条路各自的强项不同:**编码可控性** vs **格式覆盖面**。

**3. 把解码从 `TextSplitter` 挪到 `DocumentTextReader`**

第 6 项里「解码」和「切分」写在同一个类里,接入 Tika 后就别扭了 ——
解码变成了两套策略,而切分逻辑一点没变。

收窄职责后:`DocumentTextReader` 只负责「字节 → 文本」,
`TextSplitter` 只负责「文本 → 分块」。第 10 项要大改切分逻辑,
届时完全不用碰解析这块。

**4. 这里没有用「接口 + 多个实现」,而是单个类里两条分支**

前面 `DependencyChecker` 用了接口 + 集合注入,是因为**探测器数量是开放的**,
以后随时可能加新依赖。而这里的格式分流只有两条固定分支,为固定分支造接口反而绕。

**接口是为了应对「未知数量的实现」,不是为了形式上的解耦。**

**5. 设置文本长度上限,防「解压炸弹」**

一个 100KB 的 docx 解压后可能是几个 GB 的 XML。解析库默认会把内容全部读进内存,
足以把服务打挂。

防护做了两层:

1. 给 Tika 传 `maxLength`,让它在读到上限时就停下返回,而不是读完再判断
2. 拿到文本后再校验一次,超限则明确拒绝并返回 400

**6. 不把文件名传给 Tika**

Tika 支持通过 Metadata 传入文件名来辅助格式判断,但那样等于「相信用户给的名字」。
它按文件头自带探测已经足够准 —— 把可执行文件改名成 `.pdf` 传上来照样能识破。
直接传字节、让内容自己说话,更安全也更简单。

### 踩到的坑:Tika 4.0.0 无法解析依赖

`tika-parsers-standard-package:4.0.0` 在中央仓库里**只有 `.pom`,没有 `.jar`**
(4.0 把它改成了纯 pom 聚合包),Maven 直接报 `Could not find artifact`。

改用 **3.2.3** —— 有完整 jar、生态成熟、文档最多,API 与 4.x 一致。
这是「稳定可用优先于版本最新」的又一例(和 Spring Boot 版本的选择同一个道理)。

### 测试数据

用 PDFBox 和 POI(Tika 的传递依赖)生成了一份中文 PDF 和一份中文 Excel,
放进 `sample-data/`。内容刻意与已有的员工手册保持数值一致,
同时补充新信息(交通标准、申请流程、办公用品、客户招待),便于后续做检索评测。

**注意**:PDF 里的中文必须嵌入字体(用 `C:/Windows/Fonts/simhei.ttf`),
否则会显示成空白或乱码。

## 010 · 按标题层级的智能切分(本项目技术核心)

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

重写 `TextSplitter`,从「按空行切段落」升级为「标题感知 + 长度约束」的切分;
顺带把第 12 项的重新索引接口做出来(否则已有文档无法按新策略重跑)。

| 改动 | 说明 |
|---|---|
| `TextSplitter` | 标题识别 → 标题栈 → 按章节聚合 → 面包屑 → 长度约束打包 |
| `ChunkingProperties` | `rag.chunking.*`:min-size / max-size / overlap / max-heading-length |
| `DocumentChunk.metadata` | 首次映射 jsonb,写入章节路径 |
| `POST /api/documents/{id}/reindex` | 重新索引接口 |

### 关键决策

**1. 标题不再单独成块,而是作为「面包屑」前缀拼进正文**

改造前,`第一章 考勤管理` 是一个独立分块,相似度还排得很高(第 8 项实测 0.7928)。
改造后它变成正文块的前缀:

```
【星海科技差旅管理办法 > 第二章 交通标准】
2.1 高铁:单程 4 小时以内的行程,原则上乘坐高铁二等座。
...
```

一个改动同时解决三个问题:

- 检索:块自带章节语义,更容易命中
- 生成:模型看到章节路径,能理解这段在全文的位置
- **「纯标题块排名虚高」从根上消失** —— 标题不再作为独立块存在

**2. 块大小同时设上下限,而且拆分是「逐级降级」的**

| 情况 | 处理 |
|---|---|
| 段落 ≤ 上限 | 原样保留 |
| 段落 > 上限 | 按换行拆(表格行天然在这里分开) |
| 单行仍 > 上限 | 按中文句末标点拆 |
| 单句仍 > 上限 | 只能按固定长度硬切 |
| 打包后某块 < 下限 | 与相邻块合并(仅当合并后不超上限) |

越靠前的策略保留的语义越完整,所以按这个顺序降级。

**3. 章节边界优先于长度约束**

`min-size` 只在**同一个章节内部**生效。一个章节只有一小段正文时,
它不会去和别的章节合并 —— 那样会把不同主题的内容混在一起,
比"块偏短"危害更大。

所以实测里 txt 的块平均 99 字(略低于 min=150),这是有意为之,不是没生效。

**4. 表格:小表整块保留,大表按行拆并重复表头**

- 表格小于上限 → 整块保留。让模型看到完整表格,反而更容易跨行推理
  (比如「一线城市和二线城市住宿标准差多少」需要同时看两行)
- 表格超过上限 → 按行拆,**并且每一块都带上表头**

重复表头的原因:单独一行是「客户招待 | 单次不超过 1500 元 | 是」,
没有表头的话,检索到这一块完全不知道三列分别是什么意思。

**5. overlap 先实现、默认关闭**

重叠能防止答案恰好卡在块边界上造成两边都缺一半。但它也有代价:
内容重复存储、索引膨胀,而且**检索时可能命中多个高度重复的块,白白消耗 TOP K 名额**。

所以做法是:实现它、做成配置项、默认关闭,**留到第 19/20 项用评测数据决定开不开、开多少**,
而不是拍脑袋设个值。

**6. 章节路径结构化存进 `document_chunk.metadata`(JSONB)**

第 3 项建表时留了这个字段,一直空着。现在第一次用上,也第一次把 JPA 映射到 jsonb
(`@JdbcTypeCode(SqlTypes.JSON)`)。

面包屑虽然已经拼在 `content` 开头,但结构化存一份便于前端单独展示来源章节,
以后也支持按章节过滤。

### 踩到的坑:Hibernate 的 flush 顺序导致重新索引失败

**现象**:

```
duplicate key value violates unique constraint "uk_chunk_document_index"
Key (document_id, chunk_index)=(5, 0) already exists.
```

**原因**:原来用的是派生删除方法 `deleteByDocumentId`,它的做法是
「先把实体查出来,再排队删除」—— 删除动作进入 Hibernate 的动作队列。

而 **Hibernate 执行动作队列的顺序是 INSERT 先于 DELETE**。于是重新索引时:

1. 新分块先 INSERT 进来
2. 旧分块才被 DELETE
3. 新旧数据撞在唯一约束 `(document_id, chunk_index)` 上,直接报错

**解法**:改用批量删除。

```java
@Modifying
@Query("delete from DocumentChunk c where c.documentId = :documentId")
int deleteAllByDocumentId(@Param("documentId") Long documentId);
```

批量删除是一条直接的 DELETE 语句,立即执行,不参与动作队列排序,
从根上避开这个问题,顺带还少查一次数据库。

**这条经验通用性很强**:只要「先删一批、再插一批」并且两批数据有唯一约束,
就要提防 Hibernate 的 flush 顺序。

分块数量与长度分布的变化:

| 文档 | 改造前 | 改造后 |
|---|---|---|
| txt(员工手册) | 19 块,8~106 字,平均 55 | 14 块,71~134 字,平均 99 |
| pdf(差旅办法) | 23 块,8~46 字,平均 26 | **5 块**,103~164 字,平均 134 |
| xlsx(报销标准表) | 1 块,304 字 | 1 块,306 字 |

## 011 · 文档列表与删除(含第 12 项重新索引接口)

**日期**:2026-09-19
**状态**:已完成并验证

> 说明:原计划的第 12 项「重新索引接口」在第 10 项已经一并完成 ——
> 因为改完切分策略后,已有文档必须能重跑,否则那一项无法验收。
> 接口是 `POST /api/documents/{id}/reindex`。

### 做了什么

| 接口 | 说明 |
|---|---|
| `GET /api/documents?page=0&size=20` | 分页列表,按 id 倒序 |
| `DELETE /api/documents/{id}` | 删除文档:数据库记录 + 磁盘文件 |

新增 `PageResponse` 统一分页返回体。

### 关键决策

**1. 必须分页,并且给每页条数加硬上限**

代码里有一行容易被忽略但很重要的防护:

```java
int safeSize = Math.min(Math.max(1, size), MAX_PAGE_SIZE);  // MAX_PAGE_SIZE = 100
```

不加这个上限,调用方传一个 `size=100000` 就能让服务一次性把全部数据拉进内存。

**接口参数是外部输入,任何来自外部的数字都要当心。**

顺带一个知识点:`offset` 分页在数据量大、翻到很后面时会变慢
(数据库要扫描并丢弃前面所有行)。更稳的是**游标分页**(用上一页最后一条的 ID 做起点)。
本项目数据量小,`offset` 够用,但要知道这个区别。

**2. 删除顺序:先删数据库,提交之后才删文件**

这是第 5 项「先写盘后入库」的镜像问题:

| 顺序 | 崩在中间 | 危害 |
|---|---|---|
| **先删数据库,再删文件** | 留下孤儿文件 | 浪费磁盘,**安全** |
| 先删文件,再删数据库 | 库里有记录但文件没了 | 用户看得到打不开,**事故** |

**关键在于「提交之后」。** 这个方法刻意**没有**加 `@Transactional`:

如果加了,删记录和删文件就进了同一个事务,而事务提交发生在方法返回之后 ——
也就是说删文件时事务还没提交,万一后面回滚,文件已经没了。

不加事务注解,`repository.delete()` 用它自己的事务立即提交,提交完成后再动文件。

**3. 分块靠数据库级联删除,一行代码都不用写**

第 3 项建表时给 `document_chunk.document_id` 加了 `ON DELETE CASCADE`。

当时那条决策现在开始回本了:**删 `document` 一行,它的所有分块自动消失**,
不用在代码里写两遍删除逻辑,也不会留下孤儿数据。

**4. 用硬删除,不用软删除**

直接 `DELETE`,数据真的没了。更贴近「删除」的字面意思,也简单。

生产环境其实更常用**软删除**(加 `deleted` 标记位,数据保留),好处是:

- 可恢复(误删能救回来)
- 可审计(能查到谁删了什么)
- 历史引用不会断(比如某条历史回答引用了这份文档)

代价是每个查询都要记得加过滤条件,漏一个就会把已删数据查出来。
**这是个典型取舍,面试很爱问。**

**5. 返回 204 而不是 200**

删除之后没有内容可以返回,这是 `204 No Content` 的标准语义,返回体为空。

### 留给第 13 项的尾巴

第 13 项会把分块也索引到 Elasticsearch。**届时删除文档必须同步清理 ES**,

## 013 · 接入 Elasticsearch,实现 BM25 关键词检索

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

新增 `cn.ragserver.search` 包:官方 ES 客户端、索引维护、BM25 检索、调试接口、健康检查。

| 类 | 职责 |
|---|---|
| `ElasticsearchConfig` | 装配 `RestClient` 与 `ElasticsearchClient` |
| `ChunkIndexService` | 建索引、批量写入、按文档删除 |
| `EsChunkSearcher` | BM25 检索 |
| `SearchController` | `GET /api/search/bm25?q=xxx` 调试接口 |
| `ElasticsearchChecker` | 健康检查 |

### 关键决策

**1. 中文分词用 ES 内置的 `cjk` 分析器,不装插件**

这是本项最关键的一行配置。实测对比「星海科技差旅管理办法」:

| 分析器 | 切分结果 |
|---|---|
| `standard`(默认) | `星` `海` `科` `技` `差` `旅` `管` `理` `办` `法` —— **单字切分** |
| `cjk`(内置) | `星海` `海科` `科技` `差旅` `管理` `办法` —— **二元组切分** |

用默认的 standard,BM25 的逆文档频率会失去意义:
几乎每份中文文档都含「的」「管」「理」这类字,这些词的 IDF 趋近于 0,
真正有区分度的词权重被淹没,打分退化成近似随机。

选 `cjk` 而不是装 IK 分词器的理由:它是 ES 内置的,**不用重建容器**,
不用改 Docker 镜像或往容器里拷插件。生产环境通常还是用 IK(基于词典,
分词更准,还能自定义业务词汇),这条写进 README 的「上生产要改什么」。

**2. 用官方 Java 客户端,不用 Spring Data Elasticsearch**

| | Spring Data ES | 官方 Java Client |
|---|---|---|
| 版本 | 与 Spring Boot 强绑定 | 独立控制 |
| 定位 | CRUD 导向(声明 Repository) | 检索导向 |
| 控制力 | 弱 | 强 |

我们需要的是检索能力(多路召回、打分、融合),不是 CRUD。

**3. 字段类型:要检索的用 `text`,要精确匹配的用 `keyword`**

| 字段 | 类型 | 原因 |
|---|---|---|
| `content` | `text` + cjk | 这是要全文检索的字段 |
| `fileName` / `section` | `keyword` | 精确匹配和聚合用 |

如果 `fileName` 也用 `text`,「员工手册」会被切成「员工」「工手」「手册」,
按文件名过滤就完全不可靠了。

**4. 用 `chunkId` 作为 ES 的文档 `_id`**

同一个 id 重复写入是覆盖而非追加,天然幂等。

**5. 健康检查自己写一个**

因为用的是官方客户端而不是 Spring Data ES,Actuator 自带的
Elasticsearch 健康指示器不会生效。**这正好兑现了第 4 项埋的那个伏笔** ——
当时说「等接入 Actuator 不认识的依赖时再写自定义 HealthIndicator」,现在就是那个时刻。

### 踩到的坑一:客户端与服务端版本不匹配

**现象**:

```
node: http://localhost:9200/, status: 200,
[es/cluster.health] Failed to decode response
Missing required property 'HealthResponse.unassignedPrimaryShards'
```

HTTP 状态是 200,说明服务端一切正常,是**客户端反序列化失败**。

**原因**:Spring Boot 3.5.7 默认管理的 ES 客户端是 **8.18.8**,
而 docker-compose 里起的服务端是 **8.15.0**。8.18.8 的响应模型要求
`HealthResponse` 必须包含 `unassignedPrimaryShards` 字段,8.15.0 的响应里没有。

**解法**:覆盖 Spring Boot 的默认值,把客户端和服务端都钉到 8.15.0。

```xml
<elasticsearch-client.version>8.15.0</elasticsearch-client.version>
```

这个属性同时管 `elasticsearch-java` 和 `elasticsearch-rest-client`。

**通用原则:客户端库和服务端版本对齐,能省掉一整类「看起来很莫名其妙」的报错。**

### 踩到的坑二:重新索引时 ES 里产生重复数据

**现象**:数据库里 20 个分块,ES 里却有 26 条,检索结果里出现完全相同的两条。

**原因**:ES 那边用 `chunkId` 做 `_id`,重复写同一个 id 确实是覆盖。
**但重新索引时数据库是「先删旧分块、再插新分块」,新分块会拿到全新的自增 id。**

也就是说新旧两批数据的 `chunkId` 根本不一样,覆盖无从谈起 ——
老的分块就一直留在索引里了。

**解法**:索引时显式按 `documentId` 先清一遍 ES,再写新数据。

```java
chunkIndexService.deleteByDocumentId(document.getId());
chunkIndexService.indexChunks(buildSearchDocuments(...));
```

**教训**:「用业务主键做 _id 就能幂等」这个结论只在**主键不变**的前提下成立。
只要数据是「删了重建」,主键就变了,必须显式清理。

### 观察到的现象:bulk 写入后不刷新,立刻统计会少数据

写完立刻查 `_count`,得到 19 而不是 20;加一次 `_refresh` 再查,是 20。

这是 ES 的**近实时**特性:默认每秒自动刷新一次,新写入的数据最多 1 秒后才对检索可见。

代码里**刻意没有在每次写入时加 `refresh=true`** ——
每次 refresh 都要重建 Lucene 段,写入吞吐会明显下降。
对「上传后马上提问」这个场景,1 秒延迟可以接受。

### 验证结果

```
重新索引 3 个文档  →  全部 INDEXED(14 / 5 / 1 块)

健康检查:
  {"name":"Elasticsearch","status":"UP","costMs":22}

ES 文档总数(强制 refresh 后):20   = 数据库分块数 14+5+1  ✓

BM25 检索:
  "团建"    → 命中 Excel 表格块(score 1.61)
  "高铁"    → 命中 PDF「第二章 交通标准」(score 3.55)
  "打车费"  → []   ← 文档里写的是「市内交通」,字面完全不匹配
```

**最后一条尤其重要**:它用实测数据证明了**单靠 BM25 是不够的** ——
用户永远不会照着文档的原词提问。这正是第 14、15 项要做混合检索的原因。

## 014 · 两路召回,抽成统一接口

**日期**:2026-09-19
**状态**:已完成并验证

### 做了什么

把原本各写各的两套检索代码,收进一个统一接口后面。

| 类 | 职责 |
|---|---|
| `ChunkRetriever`(接口) | 一路召回的统一抽象:`name()` + `retrieve(query, topK)` |
| `VectorChunkRetriever` | 向量召回,内部负责把问题转向量 |
| `EsChunkSearcher` | BM25 召回,实现同一个接口 |
| `HybridChunkRetriever` | 编排多路召回 |
| `HybridRecallResult` | 多路结果,按路名分组返回 |

### 关键决策

**1. 为什么要抽这个接口**

第 15 项(RRF 融合)和第 16 项(Rerank 精排)要站在两路之上工作。
它们只应该知道「我拿到了一路召回结果」,不该关心底下是 pgvector 还是 Elasticsearch。

**接口是为了让上层不受下层变化影响** —— 以后换分词器、加一路召回,
上层代码一行都不用改。这和 `DependencyChecker` 是同一个模式。

**2. 用「集合注入」而不是直接依赖两个具体实现**

`HybridChunkRetriever` 注入的是 `List<ChunkRetriever>`,Spring 自动收集所有实现。

好处有两个:

1. 新增一路召回只需要写个新实现类,编排类一行都不用改
2. **避免了包之间的循环依赖** —— `retrieval` 包不需要反过来依赖 `search` 包

顺序用 `@Order` 固定(向量 1、BM25 2),保证融合时的结果顺序是确定的。

**3. 接口参数是「查询文本」而不是「向量」**

需要向量的实现自己负责把文本转向量。这样上层调用时不用区分
「这一路要不要先向量化」—— 调用方式完全统一。

**4. 召回取 50,不取最终要用的 5**

| 阶段 | 目标 |
|---|---|
| 召回 | 宁可多召回,不可漏 —— **漏了后面怎么救都救不回来** |
| 精排 | 从召回的池子里挑出真正最相关的几条 |

50 是经验起点,第 20 项做参数对比来决定。

**5. 两路分数不可比(第 15 项的伏笔)**

实测数据很直观:

```
BM25 "高铁"   得分 3.85
BM25 "出差住宿" 得分 6.42
向量相似度    始终在 0 ~ 1 之间
```

BM25 得分没有上界,余弦相似度被限制在 0~1。**直接相加等于让 BM25 天然压过向量结果**,
而且这个压制的程度还随查询词长短、文档长度变化,完全不可控。

所以第 15 项会用 **RRF(基于排名而不是分数)** 来融合。

**6. 先串行,不并行**

两路召回互相独立,理论上可以并行。但算一下收益:

```
向量那路:调 embedding API 约 500ms + pgvector 查询几毫秒
BM25 那路:ES 查询约 20ms
```

并行最多省 20ms,而总耗时是 500ms 量级 —— **为了 4% 的收益引入线程池和并发复杂度,
不划算。** 这个判断记下来,第 23 项以实测数据为准再决定。

### 验证结果

`GET /api/search/hybrid?q=xxx&size=3`,三组对比:

| 查询 | vector 路 | bm25 路 |
|---|---|---|
| **打车费** | 3 条,第 2 名正是「市内交通:凭发票实报实销」(0.712) | **0 条** |
| **高铁** | 3 条,第 1 名正确(0.749),后面是噪声 | **1 条,得分 3.85** |
| **出差住宿能报多少** | 第 1 名 Excel(0.784),第 2 名 PDF 住宿标准(0.781) | 第 1 名 Excel(6.42),**PDF 住宿标准没进前三** |

这张表是本项最有价值的产出:

- 「打车费」证明**只有向量能处理换一种说法的提问**
- 「高铁」证明**BM25 在精确词上的召回更干净**
- 第三个查询证明**两路的排序可以完全不同** —— 同一份文档在一路排第 2、在另一路掉出前三

**两路互补不是理论推断,是实测出来的。**

## 015 · 用 RRF 融合两路结果

**日期**:2026-09-20
**状态**:已完成并验证

### 做了什么

| 新增/改动 | 说明 |
|---|---|
| `RrfFusion` | RRF 融合,只用排名不用分数 |
| `RetrievalProperties.rrfK` | 新增配置项,默认 60 |
| `GET /api/search/fused` | 融合后的排名调试接口 |
| `ChatService` | 问答链路从「只用向量召回」切到「两路召回 + RRF 融合」 |
| 字段改名 | `RetrievedChunk.similarity` → `score` |

### 关键决策

**1. RRF 的公式与 k 的取值**

```
RRF得分(文档) = Σ  1 / (k + 该文档在这一路里的排名)
             各路
```

k 取 60(RRF 原论文推荐值)。它的作用是削弱排名靠前的绝对优势:
k 大 → 融合更平均;k 小 → 更偏向各路第一名。

好消息是 **RRF 对 k 并不敏感**,30~100 之间结果差别不大,所以不需要为它专门调参。

**2. 为什么不用加权求和**

直觉上 `0.7 × 向量分 + 0.3 × BM25分` 更直接,但实际行不通:

| 问题 | 说明 |
|---|---|
| 分数尺度不同 | 余弦相似度 0~1;BM25 实测 1.6 / 3.8 / 6.4,无上界 |
| 必须先归一化 | 但归一化方式没有标准答案(min-max? z-score?) |
| 归一化本身不可靠 | 用全局最大最小值时,新来一条异常数据会把所有分数压扁 |
| BM25 分数还依赖查询 | 同一份文档在不同查询下的分数根本不可比 |

**RRF 只用排名,完全绕开归一化问题**,这也是它被广泛采用的原因。

**3. 得分相同时按 chunkId 排序**

`Comparator` 里显式加了 `.thenComparingLong(entry -> entry.getKey())`。

看起来是个可有可无的细节,但很重要:**不确定的排序结果会让「改了什么导致效果变化」
变得无法分析。** 同样的输入必须永远得到同样的输出顺序。

**4. 字段改名:`similarity` → `score`**

这个字段原本叫 `similarity`,但它的含义已经混乱了:

```
向量路  -> 余弦相似度,0~1
BM25 路 -> BM25 得分,无上界
RRF 后  -> RRF 得分,0.0X 量级
```

同一个字段名承载三种含义完全不同的东西,是个明确的设计味道。
改名成中性的 `score`,并在注释里写清楚:**含义取决于产生它的那一步**。

### 观察:RRF 的价值与局限,同时出现了

查询「出差住宿能报多少」,`recall-size=5`:

| | 向量路 | BM25 路 |
|---|---|---|
| #1 | Excel 报销标准表 | Excel 报销标准表 (6.42) |
| #2 | 差旅办法 第三章 住宿标准 | 员工手册 2.1 报销标准 (5.46) |
| #3 | 员工手册 2.1 报销标准 | 差旅办法 第五章 违规处理 (2.92) |
| #4 | 差旅办法 第五章 违规处理 | 差旅办法 第一章 出差申请 (2.29) |
| #5 | 差旅办法 第二章 交通标准 | 差旅办法 第四章 补贴与报销 (2.21) |

RRF 融合之后:

| 排名 | RRF 得分 | 内容 | 两路原始排名 |
|---|---|---|---|
| 1 | 0.0328 | Excel 报销标准表 | 向量 #1 + BM25 #1 |
| 2 | 0.0320 | 员工手册 2.1 报销标准 | 向量 #3 + BM25 #2 |
| 3 | 0.0315 | 差旅办法 第五章 违规处理 | 向量 #4 + BM25 #3 |
| **4** | **0.0161** | **差旅办法 第三章 住宿标准** | **只有向量召回(#2)** |

**这张表同时展示了 RRF 的价值和它的局限:**

价值 —— 前三名都是「两路都认可」的文档,得分明显高出一档(0.032 vs 0.016)。

局限 —— **「第三章 住宿标准」本来是向量路排第 2、最贴题的那一块,
融合后掉到了第 4**,因为 BM25 没召回它。而「第五章 违规处理」这种只擦边的块,
因为两路都排在中上,反而升到了第 3。

**RRF 只看排名,不看内容。它无法判断一条分块到底能不能回答问题。**

**这正是第 16 项要做精排的原因 —— 而且现在有具体的数据支撑这个论点,不是理论推断。**

### 另一个诚实的发现:小表格整块保留的代价

模型看到了所有行,把相邻行的信息串到了一起。

这不是致命问题(团建本身确实需要发票),但它说明:
**整块保留小表格,在跨行推理上方便的同时,也带来了行与行之间串味的风险。**

一个可能的改进方向:表格按行拆,但每行都带上表头。
这一条留给第 19/20 项用评测数据判断到底哪种更好。

|---|---|
| 事实标准 | 社区资料最多,面试官大概率认识,不用花时间解释 |
| 参数规模 | 568M。精排要**逐条**跑模型,模型大小直接决定延迟和花费 |
| 中文场景 | 智源出品,中文是主场 |
| 上下文 | 8K,而我们的分块最长才 500 字 |

顺带排除掉的:`Qwen3-VL-Reranker-8B` 是**视觉-语言**多模态模型,
我们是纯文本场景,用它既慢又贵,还会被问"为什么用视觉模型做文本重排"。

**2. 精排候选数上限设 20**

精排是整个链路里最贵最慢的一步 ——
召回可以预先建索引,精排只能对每一条候选逐条跑模型。

20 的取舍:RRF 融合后的前 20 条基本已覆盖正确答案,再往后收益很小,
却会让延迟和花费线性增长。

**3. 用 `RestClient`,并且显式设置超时**

```java
SimpleClientHttpRequestFactory factory = new SimpleClientHttpRequestFactory();
factory.setConnectTimeout(...);
factory.setReadTimeout(...);
```

**默认的 `RestClient` 没有读超时。** 外部接口一旦挂起,
请求线程会被无限期占住,并发一上来整个服务就卡死了。

**4. 用 `@JsonProperty` 处理第三方接口的 snake_case,不改全局配置**

硅基流动的字段是 `top_n`、`relevance_score`,而 Java 侧是 camelCase。

没有去配 `spring.jackson.property-naming-strategy=SNAKE_CASE`,
因为那会把我们自己的接口返回也一起改掉。
**第三方接口的命名风格不该污染自己的接口契约。**

**5. 第三方返回体必须加 `@JsonIgnoreProperties(ignoreUnknown = true)`**

不加的话,对方一加字段我们就反序列化失败。
**对于不由自己控制的接口,永远要允许未知字段。**

**6. 抽出 `RetrievalPipeline`,让问答接口和调试接口共用一套代码**

如果各写一遍,调参时很容易只改了一处,两边结果对不上 ——
而调试接口存在的意义恰恰是「反映问答链路真实发生了什么」。

### 验证结果:精排修正了 RRF 的错误

这是本项最有价值的一组对比。查询「出差住宿能报多少」:

**RRF 融合后:**

| 排名 | RRF 得分 | 内容 |
|---|---|---|
| 1 | 0.0328 | Excel 报销标准表 |
| 2 | 0.0320 | 员工手册 2.1 报销标准 |
| 3 | 0.0315 | 差旅办法 第五章 **违规处理** ← 擦边内容 |
| 4 | 0.0161 | 差旅办法 第三章 **住宿标准** ← 最贴题的掉到第 4 |

**精排之后:**

| 排名 | 精排分数 | 内容 |
|---|---|---|
| 1 | **0.8607** | 员工手册 2.1 报销标准 |
| 2 | 0.8571 | Excel 报销标准表 |
| 3 | **0.7498** | 差旅办法 第三章 **住宿标准** ← 升上来了 |
| — | — | 违规处理 **被踢出前三** |

**精排模型正确判断出「违规处理」回答不了"住宿能报多少"这个问题。**

另外做了一次直接的接口对比,更能说明 Cross-encoder 的判别力:

```
问:出差住宿能报多少
  0.9467  出差住宿:一线城市每晚不超过 500 元...     <- 正确答案
  0.0048  虚报差旅行程与票据的...                  <- 擦边
  0.00003 公司实行标准工时制...                    <- 无关
```

正确答案与擦边内容差了 **200 倍**。而 RRF 的得分前几名只差 2 倍(0.032 vs 0.016),
根本分不出好坏 —— **这就是 Cross-encoder 存在的意义。**

### 一个观察:无关问题仍然调用了大模型

问「今天天气怎么样」时:

```
召回:仍然返回了若干分块(向量召回总会返回"最相似的",哪怕都很不相关)
精排:这些分块的分数会很低
但当前代码仍然调用了大模型,由模型自己回答"资料中没有找到相关内容"
```

也就是说:**明明精排已经知道"没有相关内容",我们却还是花了一次大模型调用。**

一个改进方向:给精排分数设一个阈值,全部低于阈值就直接返回固定话术,
不调用大模型。这能省一次调用、降低延迟,而且比让模型自己判断更可靠。

阈值需要实验确定,留给第 19/20 项。

### 验证结果

| 提问 | 回答 | 耗时 |
|---|---|---|
| 出差住宿能报多少? | 一线 500 / 二线 350 / 其他 250 | 4653ms |
| 虚报差旅会怎样? | 全额追回报销款并记入个人诚信档案 | 2824ms |
| 今天天气怎么样? | 资料中没有找到相关内容(0 引用) | 1548ms |

延迟的构成:向量化约 1s + 召回和精排约 1s + 大模型生成约 2.5s。
第 23 项会针对这三段分别做优化。

| 类型 | 数量 | 考察什么 |
|---|---|---|
| direct(直接型) | 65 | 基础检索 |
| paraphrase(改写型) | 40 | **语义检索** |
| precise(精确型) | 25 | **关键词检索** |
| unanswerable(不可回答) | 20 | **防幻觉** |

**第三步:写自动校验工具** `tools/ValidateEval.java`。

### 关键决策

**1. 先扩充语料,再写评测集**

原来的语料只有 20 个分块,硬造 150 条问题会大量重复,
而且"从 20 个块里找一个"这个任务太简单,评测出来的数字没有区分度。

扩到 35 个分块后,每条关键短语平均命中 **1.3 个分块** ——
既说明标注是准的,也说明这个检索任务有实际难度。

**2. 标准答案用「关键短语」标注,不用分块 ID(本项最关键的决策)**

直觉做法是标注"答案在第 137 号分块里"。但**切分策略一变,分块 ID 就全变了** ——
而我们恰恰要用这套评测集来对比不同切分策略,那样它立刻就作废了。

改用「关键短语」:

```json
{"id":"q028","question":"一线城市出差住宿每晚上限是多少?",
 "keyPhrases":["一线城市","500 元"], ...}
```

命中判定:**检索结果里存在一条分块,包含全部 keyPhrases**。

这个判据看起来很严,但它是合理的 —— 如果「一线城市」和「500 元」被切到了两个分块里,
大模型也确实拿不到完整信息,那这道题本来就该算没答对。

**这样评测集就能跨切分策略复用**,第 20 项的对比实验才能做。

**3. 评测集必须按问题类型分类**

两路召回的强项完全不同(第 14 项实测:BM25 对「打车费」完全无能为力)。
**按类型分开统计,才能看出「混合检索到底在哪些类型的问题上起了作用」。**
统一成一个总分,这个信息就丢了。

**4. 用程序自动校验大模型的输出,而不是靠人工审核**

校验三件事:

| 检查 | 目的 |
|---|---|
| JSON 解析 + id/问题去重 | 数据本身没问题 |
| 可答性:keyPhrases 必须能在某个分块里找到 | 防止标注错误 |
| 区分度:命中分块数不能太多 | 防止 keyPhrases 太泛,失去评测意义 |

**用程序校验大模型的输出,比纯人工审核高效得多**,而且这个过程本身也是面试可以讲的内容。

### 验证结果

```

  重复 id: 0,重复问题: 0
  按类型: {direct=65, paraphrase=40, precise=25, unanswerable=20}

== 2. 可答性检查 ==
```

首轮校验发现了 1 条重复问题(q056 与 q122 文字完全相同),已修正。

- 语料是**合成**的,不是真实企业文档。好处是内容可控、标注准确;
  代价是语言风格比真实文档规整,真实场景的效果会打折扣。

## 018 · 评测脚本与四种配置对比(含原第 19 项)

**日期**:2026-09-20
**状态**:已完成并验证

> 说明:原计划的第 19 项「跑三种配置对比,输出表格」在本项中一并完成 ——
> 评测脚本本来就是为对比而写的,做完自然就有了那张表。

### 做了什么

| 类 | 职责 |
|---|---|
| `EvaluationQuestion` | 评测题目的数据结构 |
| `RetrievalMode` | 四种待对比的检索配置 |
| `EvaluationMetrics` | 指标计算与累加 |
| `EvaluationRunner` | 读评测集、跑配置、算指标、渲染报告 |
| `EvaluationMain` | 命令行入口 |

### 关键决策

**1. Hit Rate 和 MRR 两个指标都要,不能只看一个**

| 指标 | 定义 | 衡量什么 |
|---|---|---|
| Hit@5 | 前 5 条里存在至少一条命中的题目占比 | **有没有找到** |
| MRR | 第一条命中位置的倒数的平均值 | **排得靠不靠前** |

一个系统可能 Hit@5 很高但 MRR 很低(正确答案总在第 3、4 名),
**那说明召回没问题、排序有问题**。只看一个指标看不出这个区别。

**2. 不做成 Web 接口,做成命令行入口**

150 题 x 4 种配置,实测跑了约 2.5 分钟(不算最慢的精排配置)。
放进 HTTP 请求里必然超时,而且评测是一次性批处理任务,
本来就不该占用常驻的服务端口。

用 `WebApplicationType.NONE` 启动 Spring 容器 ——
**不启动 Tomcat,但复用完整的依赖注入,跑完自动退出。**
额外好处是能在 IDEA 里直接右键运行。

**3. 评测集文件路径做成多候选**

从项目根目录跑和从 `rag-server` 目录跑,相对路径不一样。
写死一个路径必然在另一种情况下找不到文件,所以依次尝试几个候选路径。
报告也写到评测集旁边,而不是当前工作目录 —— 保证两次运行的产出落在同一处。

**4. 不可回答型题目不参与 Hit Rate / MRR**

它们没有关键短语,考察的是"系统会不会承认自己不知道",那是另一类指标。
**混进 Hit Rate 里只会污染数据。**

当前 20 条不可回答型题目尚未纳入评测,这是已知缺口,留给后续。

### 评测结果

> **注:本节数字来自 6 份文档 / 45 个分块的语料。**
> 后来语料扩充到 12 份 / 91 块, 所有配置的指标都下降了 ——
> 那是任务变难, 不是检索退化。
> 当前语料下的数字见 `eval/report.md` 和 README 的「效果评测」一节。

**总体:**

| 配置 | 题目数 | 命中数 | Hit@5 | MRR | 耗时 |
|---|---|---|---|---|---|
| 向量 | 130 | 129 | 99.2% | 0.9374 | 33s |
| BM25 | 130 | 128 | 98.5% | 0.9551 | 2s |
| 混合 | 130 | 130 | **100.0%** | 0.9628 | 35s |
| 混合+精排 | 130 | 130 | **100.0%** | **0.9833** | 81s |

**按题型 —— Hit@5:**

| 配置 | direct | paraphrase | precise |
|---|---|---|---|
| 向量 | 100.0% | 100.0% | **96.0%** |
| BM25 | 100.0% | **95.0%** | 100.0% |
| 混合 | 100.0% | 100.0% | 100.0% |
| 混合+精排 | 100.0% | 100.0% | 100.0% |

**按题型 —— MRR:**

| 配置 | direct | paraphrase | precise |
|---|---|---|---|
| 向量 | 0.9544 | 0.9458 | **0.8800** |
| BM25 | **1.0000** | **0.8542** | **1.0000** |
| 混合 | 0.9846 | 0.9167 | 0.9800 |
| 混合+精排 | 0.9923 | **0.9708** | 0.9800 |

### 三个有数据支撑的结论

**结论一:两路召回各有明确短板,而且是互补的**

| | 向量 | BM25 |
|---|---|---|
| 精确型 Hit@5 | **96.0%**(漏 1 题) | 100% |
| 改写型 Hit@5 | 100% | **95.0%**(漏 2 题) |
| 精确型 MRR | **0.8800** | **1.0000** |
| 改写型 MRR | 0.9458 | **0.8542** |

向量怕精确词(专有名词、编号),BM25 怕换一种说法 ——
**这个规律在第 14 项是定性推测,现在是定量数据。**

**结论二:混合补齐了短板,但代价是排序被"拉平"**

混合把两个短板都补到了 100% —— 这是它的价值。

但注意 MRR:混合是 0.9846 / 0.9167 / 0.9800,
**每一档都比单路的长板低**(BM25 单路在 direct 和 precise 上都是满分 1.0000)。

原因是 RRF 只用排名不用分数:它把两路的排名平均了一下,
对"一路排第 1、另一路没召回"的文档反而不利。

**这是 RRF 的固有代价,不是实现 bug。**

**结论三:精排的价值集中在改写型**

精排把 paraphrase 的 MRR 从 0.9167 提到 **0.9708,提升 5.9%**,
direct 从 0.9846 提到 0.9923,precise 保持不变。

这符合预期 —— Cross-encoder 能看到问题和文档的完整交互,
**最擅长的正是"换了说法还能不能对上"这件事**。

### 必须诚实说明的局限:天花板效应

四种配置的 Hit@5 全部在 98% 以上,**这说明评测任务对当前语料来说偏简单了**。

根本原因是语料只有 35 个分块 —— 从 35 个候选里找 5 个,
随机命中率也有 14%,何况向量和 BM25 都不算差。

**后果**:Hit@5 这个指标已经接近饱和,区分度主要靠 MRR。
要看更明显的差异,需要更大的语料,或者更严格的指标(比如 Hit@1)。

**这一点必须写进简历和面试陈述里** —— 报一个"Hit@5 从 99.2% 提升到 100%"
听起来很漂亮,但内行一看就知道是任务太简单。

## 020 · 分块参数调优实验

**日期**:2026-09-20
**状态**:已完成并验证

### 做了什么

给评测入口加上「先重新索引」和「只跑指定配置」两个开关,
把分块参数变成了可以批量实验的变量,跑了两轮共七组对比。

最终把 `max-size` 从 500 调到 **120**,`min-size` 从 150 调到 **60**。

### 关键决策

**1. 让评测程序自己负责重新索引**

改完分块参数,已有的分块还是按旧规则切的,必须重跑。
与其手动「先调一个接口、再跑评测」,不如让评测程序先重新索引再评测 ——
**一条命令跑完一组实验**,七组实验只是七条命令的差别。

**2. 报告里加上 Hit@1**

第 18 项的实测显示 Hit@5 已经全部 98% 以上,**再往上没有空间了**。
Hit@1 问的是「排在第一位的那条对不对」,在饱和的指标上更严格才有区分度。

这个指标是后面发现问题的关键。

**3. 只跑「混合+精排」一种配置**

四组 × 四种配置 = 16 次完整评测,要跑十几分钟。
而配置对比在第 18 项已经做过了,这一项要回答的是「哪个分块参数更好」。

### 第一轮实验:四组参数结果完全相同

| 组 | min | max | overlap | Hit@1 | Hit@5 | MRR |
|---|---|---|---|---|---|---|
| A | 80 | 250 | 0 | 96.9% | 100.0% | 0.9833 |
| B | 150 | 500 | 0 | 96.9% | 100.0% | 0.9833 |
| C | 300 | 900 | 0 | 96.9% | 100.0% | 0.9833 |
| D | 150 | 500 | 50 | 96.9% | 100.0% | 0.9833 |

**四组指标一模一样,精确到小数点后四位。** 这要么是程序有 bug,要么是参数根本没生效。

于是直接去数实际分块数:

| 配置 | 实际分块数 |
|---|---|
| max=900 / 500 / 250 | **35(完全相同)** |
| max=120 | 45 |
| max=50 | **107** |

**原因找到了**:这几份文档的章节正文都在 250 字以内,
所以只要 `max >= 250`,这个阈值就**永远不会被触发**。
A、B、C 三组在物理上就是同一份切分结果,指标当然完全一样。

而 `min` 同理 —— 每个章节的正文都超过 min,没有可合并的对象,所以调它也没有效果。

**这条经验很值得记**:

> **参数调优的前提是这个参数在当前数据上真的会生效。**
> 在设计实验之前,先确认参数的不同取值会导致不同的行为 ——
> 否则你会得到一组漂亮的、毫无意义的「结果相同」。

### 第二轮实验:用会真正触发的参数

> **注:本组实验的语料是 6 份文档(对应 35 ~ 107 个分块)。**
> 语料后来扩充到 12 份, 这组实验已经**原样重跑过一遍**, 结论不变, 见下面的「第三轮」。

改用 `max` 会真正切分文档的取值,重跑:

| 配置 | 分块数 | Hit@1 | Hit@5 | MRR |
|---|---|---|---|---|
| 粗粒度 max=500 | 35 | 96.9% | 100.0% | 0.9833 |
| **中粒度 max=120** | **45** | **98.5%** | 100.0% | **0.9923** |
| 细粒度 max=50 | 107 | 96.2% | **99.2%** | 0.9769 |

还补跑了一组 `min=60, max=120`(因为第一轮的配置里 min > max,不自洽),
结果与 `min=150, max=120` **完全一致** —— 再次印证 min 在本语料上不起作用。

### 结论:效果随粒度呈倒 U 型

```
Hit@1
 98.5% |            ●  max=120 (45 块)
       |
 96.9% |  ● max=500        ● max=50
       |  (35 块)          (107 块)
       +--------------------------------
          粗               中          细
```

**太粗和太细都更差,中粒度最好。** 原因各不相同:

| 粒度 | 问题 |
|---|---|
| 太粗(35 块) | 一个块里混了多个要点,检索时相关性被"稀释" |
| 太细(107 块) | 每块上下文不足、语义不完整;候选数变多也引入了更多干扰 |

**`max=50` 那组的 Hit@5 还首次跌破了 100%**(99.2%)——
说明切得太碎时,连"前 5 条里能不能找到"都保证不了了。

最终选定:`min-size = 60`,`max-size = 120`。

### 第三轮实验:语料扩充到 12 份之后重新验证

上面的实验是在 6 份文档的语料上做的。后来加入了 `sample-data/tech-kb/` 的 6 份技术文档,
语料变成 12 份,于是把这组实验**原样重跑了一遍**。
(可复现脚本:`tools/chunking-experiment.sh`,用法见脚本头部注释。)

| 配置 | 分块数 | Hit@1 | Hit@5 | MRR |
|---|---|---|---|---|
| 粗粒度 max=500 | 61 | 96.9% | 100.0% | 0.9833 |
| **中粒度 max=120** | **91** | **97.7%** | **100.0%** | **0.9885** |
| 细粒度 max=50 | 208 | 96.2% | 99.2% | 0.9769 |

分块数大约翻倍(35→61、45→91、107→208),与语料翻倍一致,说明参数确实按预期生效。

**结论没有变:倒 U 型依然成立,`max=120` 仍然是新语料下的最优值。**
所以 `application.yml` 里的默认值保持 120。

两点值得单独记下来:

**一、两个极端配置的指标与旧语料完全一致,而且可复现。**

`max=500` 和 `max=50` 两组的三个指标与 6 份文档时**逐位相同**
(96.9% / 100.0% / 0.9833 和 96.2% / 99.2% / 0.9769)。
我重跑了一遍确认不是偶然。

合理的解释是:**分块是逐文档进行的,新增文档不会改变原有文档的分块结果**;
而新增的 6 份技术文档在这些题目的前 5 名里都挤不进去,
所以名次一个都没动。这个解释**没有进一步验证**,只是与数据一致 ——
如实记在这里,不作为结论使用。

**二、只有 `max=120` 那一组指标下降了。**

98.5% → 97.7%,和全量评测报告的降幅吻合。
说明中粒度切出来的块彼此更接近,候选集翻倍带来的干扰在这一档最容易显现。
换句话说,**参数结论的敏感程度本身也依赖语料规模**。

### 关于 overlap 的结论

第一轮的 D 组(overlap=50)与基准组结果相同。

在那个配置下 `max=500`,块本身就没有被切碎,自然也不存在"答案跨越块边界"的问题,
所以 overlap 无从发挥。

**overlap 的价值只在「块被切分」的场景下才体现**,而我们最终选的 max=120
确实会切分部分章节。但当前语料下它带来的收益仍然小于额外成本
(重复存储、检索时命中内容重复的块、浪费 TOP K 名额),所以保持关闭。

### 必须诚实说明的局限

1. **语料是合成的小语料**(重跑时是 12 份文档、61~208 个分块)。
    参数的最优值很可能随语料规模变化 —— 虽然扩充语料后重跑仍然指向 `max=120`,
    但两次用的是同一批合成文档,**不能直接外推**到真实业务语料。
2. Hit@5 仍然接近饱和,区分度主要靠 Hit@1 和 MRR。
3. 只调了 `min` / `max` / `overlap` 三个参数,
   没测过分块策略本身的变化(比如表格是否按行拆)。

**简历里不应该写"调优提升 X%"** —— 0.9% 的提升在这点数据量下很可能只是噪声。
应该写的是**方法论**:怎么设计实验、怎么发现参数没生效、怎么得出倒 U 型结论。

## 021 · SSE 流式输出与首字延迟

**日期**:2026-09-20
**状态**:已完成并验证

### 做了什么

| 新增/改动 | 说明 |
|---|---|
| `ChatConfig.streamingChatModel` | 新增流式模型 Bean |
| `ChatStreamService` | 流式问答的服务端实现 |
| `POST /api/chat/stream` | SSE 接口 |
| `CitationBuilder` | 从 ChatService 抽出的公共组件 |

### 关键决策

**1. 流式和非流式两个模型 Bean 都保留**

同一个模型、同一份配置,区别只在调用方式。

保留两个是因为适用场景不同:

- **流式**给前端交互用 —— 用户能看到字一个个出来
- **非流式**给评测和批处理用 —— 评测要的是完整答案文本,用流式只会徒增复杂度

**2. TTFT 包含检索时间,而且分两段上报**

完整的首字延迟 = 检索耗时 + 模型出第一个字的耗时。

检索那一段(向量化 + 召回 + 精排)要 1.5 秒,是延迟的大头之一。
所以服务端分别上报 `retrievalMs` 和 `ttftMs`,**便于定位瓶颈到底在哪一段**。

**3. 必须异步,否则就退化成同步了**

SSE 的做法是「立刻把 emitter 返回给容器,再在别的线程里慢慢往里推数据」。
如果直接在请求线程里生成,那就只是"响应体分块"而已,请求线程照样被占满。

线程数先给 4 个保守值,第 23 项会统一调整线程池配置。

**4. 参数校验必须放在同步阶段**

`stream()` 方法本身立刻返回 emitter,真正的生成在后台线程。

所以「问题为空」这类校验必须在**返回 emitter 之前**同步做掉 ——
否则这个错误只能以 SSE 事件的形式返回,而调用方期望的是一个 400 状态码。

**5. 发送事件的异常要吞掉**

客户端中途断开时 `emitter.send()` 会抛异常。

但那个时刻主流程往往还在正常生成 —— 为了一个"没人接收"的事件把整次生成打断,
只会让服务端日志里堆满无意义的报错。所以这里只记 debug 日志,不往上抛。

**6. 抽出 `CitationBuilder`**

非流式和流式两条链路都要组装引用。如果各写一份,
**同一个问题在两种调用方式下可能给出不同的引用**,这是很难跟用户解释的。

抽成公共组件后,两边的判断逻辑天然一致。

### 验证结果

事件序列:

```
event:meta   data:{"retrievalMs":1482,"hitCount":3}
event:meta   data:{"ttftMs":2638}
event:delta  data:{"text":"出差"}
event:delta  data:{"text":"住宿的"}
...  共 14 个 delta 事件
event:done   data:{"sessionId":16,"answer":"出差住宿的报销标准...","citations":[...],
                   "retrievalMs":1482,"ttftMs":2638,"totalMs":3904}
```

**流式与非流式的客户端观测对比:**

| 接口 | 客户端首字节 | 用户看到第一个字 | 总耗时 |
|---|---|---|---|
| 流式 `/api/chat/stream` | **1.61s** | 2.64s | 4.13s |
| 非流式 `/api/chat` | 3.62s | **3.62s** | 3.62s |

**用户提前整整 2 秒看到内容。** 非流式是"盯着空白等 3.6 秒,然后整段刷出来";
流式是"1.6 秒看到状态,2.6 秒开始逐字出现"。

总耗时流式反而略高(4.13s vs 3.62s),属于 SSE 分帧开销和两次请求各自做检索的正常差异。
**流式的价值在于感知延迟,不在于总耗时。**

### 两个观察

**观察一:客户端的「首字节时间」不等于 TTFT**

客户端观测到 1.61s 就收到首字节,但服务端报的 `ttftMs` 是 2638ms。

差异来自服务端在检索完成后先发了一个 `meta` 事件。
这本身是好事(前端能立刻显示"正在检索…"),但它意味着
**用 `curl -w "%{time_starttransfer}"` 测出来的数字不能当作 TTFT 用**,
真正的首字延迟要看 `done` 事件里上报的 `ttftMs`。

**观察二:Excel 表格终于被拆开了**

引用里出现了 `chunkIndex` 为 0 和 1 的两条 Excel 分块。

说明第 20 项把 `max-size` 调到 120 之后,306 字符的表格**真的触发了拆分**,
而且**每一块都带上了表头** —— 第 10 项写的 `packTable` 逻辑到这里才第一次被真正执行。

### 已知局限

- **客户端断开后模型仍在继续生成**。LangChain4j 的流式接口没有提供取消机制,
  服务端只能做到"不再往断掉的连接上写",没法真正中止已经发出去的请求。
  生产环境需要用支持取消的 HTTP 客户端,或者接受这部分浪费。
- 流式响应目前不做缓存。第 22 项做缓存时需要考虑:
  命中缓存的请求是直接返回完整答案,还是把缓存的文本按片段"重放"一遍。

### 面试可能被追问

1. SSE 和 WebSocket 有什么区别?为什么这里用 SSE?
2. 为什么流式必须异步处理?直接在请求线程里写会怎样?
3. 首字延迟和总耗时分别反映什么?哪个对用户体验更重要?
4. 客户端断开连接后,服务端的模型调用会怎样?

## 022 · Redis 缓存重复提问

**日期**:2026-09-20
**状态**:已完成并验证

### 做了什么

| 类 | 职责 |
|---|---|
| `CacheProperties` | `rag.cache.*` 配置 |
| `QaCacheService` | 缓存读写 |
| `KnowledgeBaseVersion` | 全局知识库版本号 |
| `CachedAnswer` | 缓存内容 |

非流式和流式两条链路都接上了缓存。

### 关键决策

**1. 缓存整个答案,不是只缓存检索结果**

| 粒度 | 省掉什么 | 还要做什么 |
|---|---|---|
| 只缓存检索结果 | 一次 embedding + 召回 + 精排 | 仍要调大模型(约 2.5s) |
| **缓存完整答案** | 全部 | 什么都不用做 |

重复提问的场景下,用户要的就是同一个答案。既然检索结果和答案都不该变,那就缓存到底。

**2. 做「归一化后的精确匹配」,不做语义缓存**

| | 精确匹配 | 语义缓存 |
|---|---|---|
| 原理 | 问题文本做 hash | 问题向量找相似的历史提问 |
| 命中率 | 只命中一字不差的 | 能命中改写型提问 |
| **误命中风险** | **零** | **存在** |

语义缓存听起来更高级,但**它的失败模式很危险**:两个"向量很像但实际不同"的问题
会拿到同一个答案,用户得到一个答非所问的回复,而且完全不知道为什么。

权衡下来先做精确匹配,但**加上归一化**——去掉空白和中英文标点、统一小写。
这样「出差住宿能报多少?」和「出差住宿能报多少」会命中同一个键,
**在零误命中风险的前提下拿到最大的命中率提升**。

语义缓存作为已知优化方向写进 README,等有真实流量数据再评估。

**3. 缓存键里带「知识库版本号」(本项最关键的决策)**

**缓存的失败模式比它带来的收益更需要警惕。**

缓存命中时用户拿到的是"上次的答案"。如果知识库已经更新,这个答案就是错的 ——
但它读起来依然通顺、依然言之凿凿,**用户完全没有办法察觉**。

三种失效方案:

| 方案 | 做法 | 问题 |
|---|---|---|
| 全量清空 | 文档一变就 `FLUSHDB` | 粗暴,所有缓存瞬间作废 |
| 逐个删除 | 遍历找出"相关"的缓存删掉 | 很难算准影响范围:一道题引用了被删文档的分块,但缓存键和文档之间没有直接关联 |
| **版本号** | 键 = `rag:qa:v{版本号}:{问题hash}` | 旧键自动不再被查找,靠 TTL 回收 |

选第三种:**不需要遍历删除,也不会有遗漏**。
代价是旧缓存会在 Redis 里多占一会儿内存,直到 TTL 到期。

**4. 缓存故障不影响主流程**

缓存是「锦上添花」的功能,它坏掉不该让整个问答不可用。

所以 `QaCacheService` 里所有 Redis 操作都包了 try-catch:
读失败按"未命中"处理,写失败只记日志。`KnowledgeBaseVersion.current()`
读不到版本号时返回 -1,调用方直接跳过缓存。

**5. 流式接口命中缓存时不「重放」**

把缓存文本拆成多个 delta 事件重发,能让体验完全一致。
但那是**假装模型又生成了一遍** —— 用户以为系统真的跑了 4 秒,实际是把旧文本分段发出来。

选择直接发一个 `done` 事件并标记 `"cached": true`,由前端决定要不要做打字机动画。
**诚实且更快。**

**6. 命中缓存也要写会话历史**

否则用户会发现"这次提问没有出现在历史记录里"。会话记录和缓存是两回事。

### 验证结果

| 场景 | 耗时 |
|---|---|
| 首次提问(未命中) | 4.519s |
| 重复提问同一句(命中) | **0.021s** |
| 去掉问号再问(归一化后命中) | **0.019s** |
| 重新索引文档后再问(版本号已变) | 3.382s(正确失效) |

**命中缓存后从 4.5 秒降到 0.02 秒,快约 200 倍**,而且零外部 API 调用。

三个关键行为都验证通过:

1. 完全相同的提问命中缓存
2. 只差标点的提问**也**命中(归一化生效)
3. 知识库变更后旧缓存**立即失效**(版本号机制生效)

### 已知局限

- 只做精确匹配,**改写型提问不会命中**。这是刻意的取舍,不是遗漏。
- 旧版本号的缓存要等 TTL 到期才回收,期间会占内存。
  缓存量大时应改用 Redis 的 `SCAN` + 批量删除,或者直接用带版本前缀的独立 DB。
- 当前没有缓存命中率监控。生产环境应该把这个指标暴露出去
  —— 命中率长期偏低说明缓存策略没起作用。

### 面试可能被追问

1. 缓存键怎么设计?为什么要把知识库版本号放进键里?
2. 语义缓存的风险是什么?什么场景下不能用?
3. 缓存和数据库的一致性问题,你怎么处理?
4. 缓存命中率低怎么办?怎么判断是策略问题还是流量特征问题?

## 023 · 线程池统一 + 降级链 + 超时重试

**日期**:2026-09-20
**状态**:已完成并验证

### 做了什么

这一项是**收账** —— 把前面 22 项里陆续记下的 8 个「已知但未处理」的点一次性还掉。

| 改动 | 说明 |
|---|---|
| `ThreadPoolConfig` / `ThreadPoolProperties` | 线程池从硬编码改为统一配置 |
| `HybridChunkRetriever` | 单路召回失败时降级为其余通道 |
| `RetrievalPipeline` | 精排失败时降级为 RRF 排序 |
| `ChatService` / `ChatStreamService` | 大模型失败时降级为返回检索原文 |
| `FallbackAnswerBuilder` | 降级答案的统一构造 |
| `RetrievalResult` | 把「是否降级」一路传到响应里 |
| `SiliconFlowReranker` | 增加重试,并区分「值得重试」与「不该重试」 |
| `GlobalExceptionHandler` | 线程池拒绝时返回 503 而不是 500 |

### 关键决策

**1. 线程池必须设队列上限**

不设上限的队列是线上事故的经典成因:高峰期请求不断排进队列,
队列越排越长、内存一直涨,最后 OOM —— 而且**在崩溃之前系统看起来一切正常**,
只是越来越慢。等发现的时候已经晚了。

设了容量上限之后,超出的请求会被拒绝策略立刻处理掉,
调用方马上收到「服务繁忙」而不是无限等待。**快速失败比慢慢崩溃好。**

**2. 拒绝策略选 AbortPolicy,不选 CallerRunsPolicy**

CallerRuns 看起来「更友好」—— 它不丢任务,让提交任务的线程自己跑。

但对流式问答来说那是灾难:它会把生成任务压回 Tomcat 的工作线程,
于是**本该被保护的 Web 线程池反而被拖垮,保护等于失效**。

直接拒绝则让调用方立刻收到明确信号,我们把 `TaskRejectedException`
翻译成 503 返回给用户。

**3. 降级链:每一个外部依赖都有兜底**

| 挂掉的依赖 | 改造前 | 改造后 |
|---|---|---|
| 精排 API | 直接报错 500 | **降级为 RRF 排序** —— 候选池本来就有,截断即可 |
| 大模型 API | 直接报错 500 | **返回检索到的原文片段** |
| BM25(ES) | 直接报错 500 | **只用向量召回** |
| 向量检索 | 直接报错 500 | **只用 BM25 召回** |
| Redis 缓存 | 跳过 ✓ | 已实现 |

**只有所有召回通道都失败,才认为整体不可用。** 单路失败一律降级继续。

这就是「高可用」在项目里的具体形态:不是喊口号,
而是**每一个外部依赖都有明确的、经过验证的兜底行为**。

**4. 降级可以不完美,但不能瞒着**

第一版实现里精排降级只写了服务端日志,响应里的 `degraded` 标记只反映模型降级。

这意味着:精排挂了的时候,前端看到的是 `degraded=false` ——
**用户以为自己拿到的是完整链路的结果,实际少了一个环节。**

修正做法:新增 `RetrievalResult`,把「是否降级」一路传到响应里。
前端可以据此提示「当前结果未经精排」,用户也就有了判断依据。

**5. 重试要区分「值得重试」和「不该重试」**

| 失败类型 | 是否重试 | 理由 |
|---|---|---|
| 5xx 服务端错误 | ✅ | 对方临时故障,重试有意义 |
| 429 限流 | ✅ | 等一会儿再来 |
| 连接/读超时 | ✅ | 网络抖动,重试通常能成功 |
| 4xx 参数错误、密钥无效 | ❌ | **重试一万次结果也一样**,只是白白拖慢响应 |

后一条尤其重要 —— 这正是我们做降级验证时遇到的情况:
用一个无效密钥去调,重试只会让响应更慢,不会变成功。

**6. 流式降级有边界**

流式生成失败时,能不能降级成「返回检索原文」,取决于**内容吐出去了没有**:

- 一个字都还没发出去 → 可以完整降级,行为和同步接口一致
- 已经吐了一部分 → 再补一段「资料清单」只会让回答更乱,**如实报错**

### 踩到的坑:缓存把降级测试挡住了

第一次做降级验证时,把精排密钥和对话密钥分别改成无效值,结果**三次调用的
返回完全一样,而且 `degraded` 都是 false**。

排查后发现:第一次正常调用已经把这个问题的答案写进了缓存,
后面两次直接命中缓存,压根没走到精排和模型。

**这本身说明缓存工作正常**,但也说明:做降级/故障验证时,
必须先关掉缓存(`--rag.cache.enabled=false`),否则测的是缓存,不是降级。

### 关于批量插入:测量之后决定不做

第 6 项发现「`IDENTITY` 主键让 Hibernate 无法批量插入,`saveAll` 实际是一条条 INSERT」。

这次加了分块入库的计时,实测数据:

| 文档 | 分块数 | 总耗时 | 其中分块入库 |
|---|---|---|---|
| 员工手册 | 14 | 1202ms | **98ms** |
| IT 服务管理办法 | 9 | 974ms | **19ms** |
| 采购管理制度 | 6 | 828ms | **16ms** |
| 新员工入职指南 | 7 | 459ms | **15ms** |

**分块入库只占总耗时的 2~8%,其余全是 embedding API 调用。**

改成批量插入最多省几十毫秒,却要换主键策略、加一次 Flyway 迁移、承担改动风险。
而且索引是低频操作,这点时间完全无所谓。

**结论:不做。但这是"测出来之后决定不做",不是"想当然地不做"**
—— 两者的区别在于,前者在面试时能拿出数字。

### 验证结果

| 场景 | degraded | 结果 |
|---|---|---|
| 全部正常 | `false` | 正常答案 |
| **精排密钥错误** | **`true`** | **仍然答对**(自动降级到 RRF 排序) |
| **对话密钥错误** | **`true`** | 返回检索原文片段 |
| **流式 + 对话密钥错误** | **`true`** | 流式接口同样降级 |

四个场景全部符合预期。特别注意第二条 ——
**精排挂了之后系统给出的答案依然正确**,只是少了一层精判。
这就是降级的意义:质量降一档,但服务不中断。

### 还没做的

- **精排分数阈值**:第 16 项发现「无关问题时仍调用大模型」,加阈值能省一次调用。
  **已在第 24 项做过校准,结论是样本太小、阈值不可靠,决定不接入** —— 见 024。
- **评测时问题向量重复计算**:同一道题在三种配置里被向量化三次,
  可以缓存。属于评测工具本身的优化,不影响线上。
- **手动触发降级的开关**:目前验证降级要靠传无效密钥。
  生产环境应该有专门的开关来定期演练降级路径 —— **没演练过的降级等于没有降级**。

## 024 · 拒答阈值校准:验证集上失效,决定不接入

### 做了什么

给评测加上**拒答阈值校准**:用 20 道不可回答题 + 130 道可回答题,
算出一条「阈值 → 误答率 → 误拒率」的权衡曲线,并挑出一个阈值。

代码在 `RefusalCalibration`(eval 包),`EvaluationMain` 跑完四种配置后自动执行,
结果写进 `eval/report.md`。
**注意:只做了校准,没有把阈值接入问答链路。**

### 为什么需要它

第 16 项观察到:问知识库里根本没有的问题时,系统仍然会调用一次大模型 ——
因为链路的判断是「检索回来非空就生成」,而检索永远会返回前 K 条。
问一个库里没有的词(实测精排分数只有 0.0001),照样花掉一次模型调用。

如果精排分数能提前判断「这批候选都不相关」,这次调用就能省掉。
问题是阈值定多少 —— 这个数字不能拍脑袋,得用评测数据算出来。

### 关键决策

**一、两类题目,两套指标,绝不混算。**

- 不可回答题 → **误答率**:分数达到阈值就会被回答,而知识库里根本没有答案
- 可回答题 → **误拒率**:**本来答得对**(top-1 已命中)却低于阈值会被拒答

「误拒」只统计 top-1 就命中的题目。检索本身没找到答案的题不计入 ——
那种情况下拒答反而是正确行为,不该算作阈值的代价。
这也直接决定了阈值的收益上限:能避免的错答次数,顶多是「top-1 未命中」的题目数。

**二、挑阈值的规则是「约束 + 优化」,不是加权求和。**

约束:误答率 ≤ 5%;目标:在此前提下让误拒率最小。

两类错误的代价不对称 —— 误答会让用户相信一个编造的答案,
误拒只是让用户换个说法再问一次。所以先把误答压到可接受的水平,再优化误拒;
而不是给两个错误各配一个权重、求加权和的最小值,那种权重同样是拍脑袋,还不好解释。

**三、做留出验证。**

阈值是从这批数据里挑出来的,直接在挑它的那批数据上报成绩就是过拟合 ——
相当于同一套题既出题又判分。所以按题号奇偶切两半:
**偶数题挑阈值,奇数题只用于复核**。两边的差距就是过拟合程度的直接证据。

### 验证结果

**全量数据上的权衡曲线:**

| 阈值 | 误答率 | 误拒率 | 拦下的「本就答错」题 |
|---|---|---|---|
| 0.05 | 20.0% (4/20) | 1.6% (2/127) | 1/3 |
| 0.10 | 5.0% (1/20) | 4.7% (6/127) | 1/3 |
| 0.20 | 0.0% (0/20) | 5.5% (7/127) | 1/3 |

**留出验证:**

| | 不可回答题 | 本来答得对的可回答题 |
|---|---|---|
| 调参集(偶数题) | 10 | 64 |
| 验证集(奇数题) | 10 | 63 |

- 选定阈值 **0.0417**;在调参集上误答率 **0.0%**、误拒率 1.6%
- **在验证集上误答率 40.0%**、误拒率 0.0%

### 结论:不接入

三条理由,轻重排序:

**1. 收益上限本来就低 —— 只有 1 道题。**
可回答题里 top-1 就没命中的只有 3 道,曲线上每一档实际拦下的都只有 1 道。
绝大部分可回答的问题,检索本来就已经找对了,不需要阈值来救。

**2. 代价却很高 —— 最高 7 道题。**
要把误答率压到 0,阈值得提到 0.2,代价是拒答 7 道本来答得对的问题。
用 7 次误拒换 1 次避免错答,不划算。

**3. 验证集上直接失效 —— 这是决定性的。**
误答率从调参集的 0% 跳到验证集的 40%,差 40 个百分点。

第 3 条的根因是样本太小:20 道不可回答题切一半只剩 10 道,
**一道题就等于 10 个百分点**。所以这个实验的正确结论不是「阈值是 0.0417」,
而是 **「在这个样本量上,阈值定不出来」**。
要让它可用,得先把不可回答题扩到几百道。

### 备选方案与放弃原因

| 方案 | 为什么没选 |
|---|---|
| 用「第一名与第二名的差值」代替绝对分数 | 实测更差:各自最优切点下合计错 12 条,绝对分数是 6 条 |
| 用「第一名与第二名的倍数」 | 最差:20 道不可回答题全部误判。不可回答题的所有候选分数都趋近于 0,0.001/0.0004 也是 2.5 倍,比值失去意义 |
| 放宽约束、允许更高的误答率 | 那等于不装这个阈值 —— 它全部的意义就是拦住不该回答的问题 |
| 用大模型单独判断「资料够不够」 | 那就是现在的做法(Prompt 约束),不需要额外一步;区别是它每次都要调模型,而阈值本可以省掉这次调用 |

### 还没做的

- 不可回答题扩到几百道之后,这个校准才可能得出可用阈值。
- 阈值未接入 `ChatService` / `ChatStreamService`。
